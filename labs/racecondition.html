Race Condition Lab

A one-time coupon, redeemed with a check-then-act flaw. Fire requests fast enough and redeem it far more than once.

A one-time coupon guarded by a check-then-act flaw. Fire requests fast enough and several pass the check before any of them writes the result — so one coupon redeems many times.

How to use it

  1. Redeem the coupon normally.
  2. Fire concurrent requests into the gap between check and act.
  3. Redeem more times than should be possible.

What to take away

The window is between check and write

Every request reads "unused" before the first write lands. Both operations must be atomic, or the check means nothing.

Database transactions or locks are the fix

A conditional update that both checks and writes in one statement, or an explicit lock. Application-level checks around separate reads and writes will always have this gap.

Frequently asked questions

What is a TOCTOU bug?

Time-of-check to time-of-use — the general name for this class. State changes between validating something and acting on it, so the validation no longer describes reality.

Where do race conditions show up in the real world?

Coupon and voucher redemption, account balance transfers, rate limits, invite codes, and anywhere a "one time only" rule is enforced by reading then writing.
