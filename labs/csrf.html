CSRF Playground

A "bank" transfer endpoint trusts your cookie alone. Watch a malicious page forge a request on your behalf, then see a CSRF token stop it cold.

Cross-Site Request Forgery abuses the fact that browsers attach your cookies to requests automatically, whoever caused them. A malicious page makes your browser perform a real, authenticated action — then you switch on a CSRF token and watch the same attack fail.

How to use it

  1. Perform a normal transfer while logged in.
  2. Trigger the same request from an attacker page.
  3. Enable the CSRF token and watch it get rejected.

What to take away

The browser is the confused deputy

It holds your session and attaches it to any request to that origin. The server cannot tell intent from the cookie alone.

Tokens work because the attacker cannot read them

The same-origin policy stops a malicious page reading a token from your session, so it cannot include one.

SameSite cookies changed the landscape

SameSite=Lax by default in modern browsers blocks most cross-site request patterns — which reduced CSRF sharply without eliminating it.

Frequently asked questions

Is CSRF still relevant with SameSite cookies?

Less than it was, but yes. Legacy configurations, SameSite=None for third-party flows, and GET-based state changes all keep it alive.

What is the difference between CSRF and XSS?

CSRF makes your browser send a request you did not intend, without reading the response. XSS runs the attacker's code inside your origin, which is strictly worse — and defeats CSRF tokens outright.
