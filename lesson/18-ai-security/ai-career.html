Building an AI security career

You've reached the final career-focused lesson of Path 18. This closing lesson looks at where AI security fits in the broader career landscape you've built across this entire course, and offers genuine, grounded guidance for anyone wanting to specialise here specifically.

Why AI security is a distinctive career opportunity right now

Recall Path 18.2's framing — this is a genuinely young field. The OWASP LLM Top 10 (Path 18.5) was first published in 2023; the terminology, tooling, and even basic practitioner consensus are actively still forming as organisations rush to deploy LLM-powered features far faster than their security practices are maturing to match. This creates a distinctive window compared to the mature disciplines in Path 16:

Neither state is objectively "better" — mature fields offer clearer career paths and established expectations; young fields offer more room to become a genuinely recognised expert faster, at the cost of less structured guidance along the way.

The roles this field is actually creating

  • AI Red-teamer / AI Safety Researcher — directly building on Path 18.7's methodology, systematically probing deployed or pre-release models for safety and security failures. This is precisely the kind of work Ishfaq has been actively doing through platforms like Mercor and Alignerr/OpenClaw, doing LLM red-teaming and model output evaluation.
  • AI/LLM Security Engineer — building the defensive infrastructure (input/output filtering, instruction hierarchies from Path 18.3, agentic permission systems from Path 18.5's Excessive Agency mitigations) protecting real, deployed AI-integrated products.
  • Prompt Injection / Jailbreak Researcher — a genuinely specialised sub-niche within AI red-teaming, focused specifically on discovering and responsibly disclosing (Path 18.4's ethics) novel bypass techniques.
  • ML/AI Supply Chain Security — extending Path 10.4/11.5's supply chain concepts (and directly, Ishfaq's own professional trivy-action incident response background) into the AI-specific pipeline: model provenance, training data integrity, and the broader AI supply chain from Path 18.5's LLM05 category.
  • AI Governance and Policy — a less purely technical, more cross-functional role translating AI security/safety findings into organisational policy, risk management (Path 10.2's framework, applied here), and regulatory compliance as AI-specific regulation continues to develop globally.

How this connects to everything else in this course

This is worth sitting with directly: nothing in Path 18 stands alone. Every lesson in this final path explicitly built on foundations from every earlier path — the web vulnerability parallels from Path 11, the professional methodology from Path 14, the reporting discipline from Path 15, the supply chain and cloud concepts from Path 16. AI security isn't a separate field requiring you to discard everything you've learned — it's the newest, fastest-growing application of the exact same underlying security thinking this entire course has been building from Path 01 onward.

Getting started, concretely

  • Practice the hands-on labs from Path 18.3-12.4 — Gandalf and similar structured environments give genuinely legal, safe, immediately-accessible practice.
  • Read continuously — this field moves fast enough that staying current through blogs, published research, and practitioner writing (Simon Willison's prompt injection series, linked throughout Path 18.3-12.4) matters more here than in more settled fields.
  • Build something — a small RAG pipeline (Path 18.6's lab), a simple agentic tool with deliberately-scoped permissions (Path 18.5's Excessive Agency lesson applied constructively), or a red-teaming test harness (Path 18.7's lab) — hands-on building deepens understanding faster than reading alone, exactly as this entire course has emphasised from Path 01 onward.
  • Engage with the responsible disclosure ecosystem — several major AI labs now run bug bounty-style programs specifically for model safety issues, directly extending Path 15's entire methodology into this new domain.
  • Watch MITRE ATLAS and OWASP LLM Top 10 updates — both frameworks (Path 18.5-12.6) are actively evolving; following their development is itself a way of staying current with the field's evolving consensus.

Building a public portfolio in a field with few established norms

Recall Path 15.8's bug bounty career-building advice — the same principle of verifiable, public proof of skill applies here, but with a genuinely different texture given how young this field is. Where a web pentester can point to CVE credits or HackerOne reputation scores following well-established conventions, AI security's portfolio norms are still forming: a well-documented writeup of a novel jailbreak technique (submitted responsibly per Path 18.4's disclosure ethics, then published once a lab has addressed it), a contribution to an open-source red-teaming tool like Garak or PyRIT, or a detailed public breakdown of testing a specific open-source model against the OWASP LLM Top 10 can all serve as genuine portfolio pieces precisely because there isn't yet a single obvious "did this the right way" template to follow. This is a double-edged opportunity: the lack of established norms means more creative freedom in how you demonstrate skill, but also means you can't simply follow a well-worn path the way a traditional pentest career track allows — expect to spend real effort figuring out how to present your work convincingly, not just doing the work itself.

A closing thought on staying grounded

Recall Path 18.2's explicit warning against both hype and dismissiveness. As you continue in this field, resist both temptations: don't treat every AI system as reflexively, uniquely dangerous beyond what evidence supports, and don't dismiss genuine, demonstrated risks because "it's just a language model." The same rigorous, evidence-based, methodical thinking this entire course has modelled — from Path 01's legal foundations through Path 16's advanced techniques — applies exactly here too. Test carefully, report responsibly, and let the evidence from your own systematic work (not speculation in either direction) guide your conclusions.
