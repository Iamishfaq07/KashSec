Crypto — Break the XOR Cipher

Category: Crypto · Difficulty: Hard

Scenario

You've intercepted a message encrypted with a repeating-key XOR cipher — a genuinely weak but historically common encryption scheme where a short secret key is repeated over and over and XORed byte-by-byte against the plaintext. This challenge is harder than the others in this section: no encoding-format shortcuts, just a real (if classic) known-plaintext cryptanalysis technique.

Provided data

The ciphertext, as hex bytes:

2838317b21263a194b421126100002504d16402d044814562d520d3d070557001f

Remember from the briefing lesson: every flag in this section starts with the exact same 8 characters — KASHSEC{.

Your task

Recover the encryption key, then decrypt the full message.

Background — how repeating-key XOR works

XOR (exclusive-or) has a property that makes it perfectly reversible with the same key: plaintext XOR key = ciphertext, and ciphertext XOR key = plaintext again. With a repeating key shorter than the message, the key is just cycled: byte 0 of the plaintext is XORed with byte 0 of the key, byte 1 with byte 1 of the key, and once the key runs out, it wraps back to byte 0 again.

This repetition is exactly the cipher's fatal weakness, and exactly what makes it breakable with a known-plaintext attack: if you already know (or can guess) even a small chunk of the plaintext, XORing that known plaintext against the corresponding ciphertext bytes recovers the key directly — because ciphertext XOR known_plaintext = key.

Hint 1 — the cribYou already know the first 8 plaintext bytes with certainty: KASHSEC{. That's your "known plaintext," or crib, in cryptanalysis terms. Convert both the first 8 bytes of the ciphertext and the string KASHSEC{ to their raw byte values, and XOR them together, position by position.
Hint 2 — spotting the key lengthOnce you XOR the first 8 ciphertext bytes against KASHSEC{, write out the resulting 8 bytes as characters. You should see a short, readable sequence start repeating partway through — that repetition tells you exactly how long the real key is, and the non-repeating portion before it starts over is the key.
Hint 3 — decrypting the restOnce you have the key (it should be a short, readable word), XOR it — repeating it to match length — against the entire ciphertext, not just the first 8 bytes, to recover the complete plaintext message.
Show full answerXORing the first 8 ciphertext bytes against the known crib KASHSEC{ recovers the byte sequence c y b 3 r c y b — and the repetition of c-y-b starting at position 5 makes it clear the actual key is just the first 5 bytes: cyb3r. Repeating that 5-byte key across the entire ciphertext (cycling c-y-b-3-r-c-y-b-3-r... for as many bytes as the message is long) and XORing it against every ciphertext byte recovers the full original plaintext.

The flag

KASHSEC{x0r_r3p34ts_g1ve_1t_4w4y}

Bonus round — what if you didn't have a crib?

This challenge was solvable quickly because you knew the plaintext started with KASHSEC{ — a genuine, guaranteed crib. Real-world ciphertext-only attacks against repeating-key XOR rarely hand you that certainty, so it's worth understanding the general technique that works even without one.

HintThink about what repeating a key does structurally to the ciphertext, independent of what the plaintext actually says. If you XOR two ciphertext bytes that were encrypted with the *same* key byte (because they're exactly one key-length apart), what cancels out?
Show answerThe standard technique is called the Kasiski examination (or a statistical variant using the index of coincidencecorrect key length produces streams where each one was XORed with a single, consistent byte — meaning each stream is really just a simple single-byte XOR cipher, which is trivially breakable via frequency analysis (English text has a very distinctive letter-frequency fingerprint, and the single XOR byte that best reproduces that fingerprint when reversed is almost certainly the correct key byte). Wrong candidate key lengths produce streams that look statistically like random noise instead. This is exactly the technique CryptoPals' classic "Break repeating-key XOR" challenge teaches in full, referenced below — genuinely worth working through once this section's simpler crib-based version feels comfortable.

Why this matters beyond the CTF

Known-plaintext attacks against repeating-key XOR are a genuine, historically significant cryptanalysis technique — this exact class of weakness broke real ciphers long before modern cryptography existed, and it's a staple beginner exercise on platforms like CryptoPals for exactly this reason: it teaches the core insight that any predictable structure in your ciphertext (a known or guessable prefix, letter-frequency patterns, repeated blocks) can be leveraged to attack it. This is precisely why modern, properly designed encryption (AES in an authenticated mode, for instance) is built specifically to resist these categories of structural attack — repeating-key XOR predates that generation of cryptographic engineering by decades and shows exactly what it was designed to fix.

This challenge exists to build attacker intuition, not to suggest XOR ciphers belong anywhere near real systems. If you ever need real confidentiality in a project, use established, audited libraries and algorithms (AES-GCM, ChaCha20-Poly1305) — never a custom scheme, no matter how "obfuscated" it seems. This exact principle is echoed throughout Path 10 and Path 11's discussions of cryptography done wrong.
