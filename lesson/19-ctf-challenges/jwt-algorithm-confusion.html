Web — The Wrong Kind of Trust

Category: Web · Difficulty: Hard

Scenario

secure-api.kashsec-labs.test uses RS256 — asymmetric signing, meant to be the "safe" choice compared to the weak-secret and alg=none bugs from this section's earlier challenges. RS256 tokens are signed with a private key only the server holds, and verified with a matching public key that anyone can freely download — that's the whole point of asymmetric crypto, and normally it's genuinely solid.

Your task

The changelog reveals the actual vulnerability, if you read it precisely. Work out how to turn "the server trusts both algorithms" into a forged admin token.

Hint 1Re-read the changelog's last line very carefully: the verification key is chosen "based on the token's own declared alg." That means the attacker — not the server — effectively picks which key gets used for verification, just by setting the header field.
Hint 2RS256 uses the private key to sign and the public key to verify. HS256 uses one shared secret for both signing and verifying. If a poorly-written verification function is told "verify this as HS256" and blindly uses whatever key it was configured with — the server's own public RSA key — as if it were a plain HMAC secret string, what could you do with a key that is, by definition, publicly available to anyone?
Show full answerThis is algorithm confusion: change the token's header from {"alg":"RS256"} to {"alg":"HS256"}, then compute an HMAC-SHA256 signature using the server's own public RSA key — the exact text from the "Provided data" section above — as the HMAC secret string. If the server's verification code does something like jwt.verify(token, publicKey) without explicitly restricting which algorithm is acceptable, it now reads the forged token's alg:HS256 header, treats the same public key it was handed as an HMAC secret, and successfully "verifies" a signature that you — not the server's private key holder — actually produced. Because the public key is, deliberately and correctly, available to absolutely anyone, this collapses the entire asymmetric trust model. Submitting a forged token with payload {"user":"guest","role":"admin"}, signed this way, returns: {"user":"guest","role":"admin","flag":"KASHSEC{c0nfus3_th3_4lg0r1thm_st34l_th3_k3ys}"}.

Why this matters beyond the CTF

Algorithm confusion is arguably the most conceptually elegant JWT attack in this entire section, because the vulnerability isn't a weak secret or a forgotten debug flag — it's a fundamental misunderstanding, baked into the verification code, about what "the key" is supposed to mean for each algorithm. It has affected real, production JWT libraries historically, precisely because "just call verify(token, key)" looks completely reasonable at a glance. Path 21's JWT-attacks lesson covers this as the most advanced of the three classic attacks (alongside alg=none and weak secrets) — the fix is for the server to hardcode the specific algorithm it expects for a given key, and reject any token that declares a different one, rather than dynamically trusting whatever the token itself claims.

Bonus round — why doesn't this work against a well-written server?

HintThe vulnerability hinges entirely on the server dynamically choosing behavior based on the token's own alg field. What if the server simply never looked at that field to make a decision at all?
Show answerA correctly implemented server hardcodes the expected algorithm on the verification call itself — for example, jwt.verify(token, publicKey, {algorithms: ["RS256"]}) — and immediately rejects any token whose header claims a different algorithm, before ever attempting to verify a signature at all. In that world, a forged alg:HS256 token is rejected outright, regardless of what key material an attacker tries to sign it with, because the server never lets the token itself influence which verification path runs. The lesson generalizes well past JWTs: whenever a system's security-critical behavior branches based on client-supplied metadata about how to interpret client-supplied data, that's a structural red flag worth specifically hunting for.

"The client's data tells the server how to verify the client's data" is one of the most reliable smells in all of application security — it shows up in JWT algorithm confusion, in XML parsers trusting embedded DTDs (XXE), in deserialization attacks trusting a type field in the serialized payload, and elsewhere. Whenever you see this shape, assume it's exploitable until proven otherwise.
