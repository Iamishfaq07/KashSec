# Writing Technical Blog Posts

The GitHub portfolio lesson covered showcasing code. This lesson covers the complementary portfolio piece that showcases *thinking* — directly connecting to Path 15's report-writing lesson, since a genuinely good technical blog post uses nearly the same structural discipline as a professional vulnerability report, just aimed at teaching rather than disclosing to a client.

## Why writing demonstrates something code alone can't

A genuinely important, often-overlooked point: a GitHub repository shows *what* you built, but a well-written technical post shows *how you think* — the reasoning process behind a decision, the dead ends you hit and how you got past them, the tradeoffs you weighed. Hiring managers reading a strong technical writeup are evaluating problem-solving process directly, which is precisely the skill a resume bullet point or a bare code repository struggles to communicate on its own.

## What to actually write about

- **CTF write-ups** — directly connecting to Path 19's ctf-writeup-template lesson, a well-documented solve using that exact six-part structure is a genuinely strong, low-effort-to-start blog post format, since the hard thinking work is already done during the actual solve
- **"I built X" project deep-dives** — going beyond the GitHub README's what/why/how to walk through specific interesting design decisions, bugs encountered, or things you'd do differently now
- **Concept explainers** — explaining something you learned in your own words (a specific attack technique, a defensive concept) often reveals gaps in your own understanding while you write it, and a genuinely clear explanation is itself a demonstration of real comprehension, not just familiarity
- **"What I learned this month" reflections** — lower-effort but genuinely valuable for showing consistent, ongoing engagement with the field over time, directly connecting to the networking-community lesson's compounding-visibility principle

## Structure that actually works

Directly connecting to Path 15's report-writing lesson's four-part structure, adapted for a teaching context rather than a client deliverable: **context** (what problem or question prompted this), **process** (what you tried, including genuine dead ends — these make a post more credible and more useful to readers facing the same problem), **solution** (what actually worked and why), and **takeaway** (the generalizable lesson, not just the specific solved instance). A post that only shows the final, clean solution without any of the process reads as less credible and teaches readers far less than one that's honest about the messy middle.

## Where to actually publish

- **A personal blog** (even a free, simple static site) — full control, builds a genuine long-term personal asset, directly connecting to the github-portfolio lesson's ownership principle
- **Dev.to or Medium** — lower setup friction, built-in discovery through the platform's own audience, a reasonable starting point if a fully custom site feels like too much overhead initially
- **Your GitHub repository's own README or wiki** — genuinely fine for project-specific deep-dives that don't need to stand alone as independent posts

## Consistency beats perfection

:::tip A shorter post published beats a perfect post that never ships
A genuinely common trap: spending weeks trying to make a single post exhaustive and flawless, then never actually publishing it. A shorter, honest, imperfect post that ships is worth more to your portfolio (and to your own writing skill development) than an unpublished draft, regardless of how much more polished that draft theoretically could become — directly connecting to the ai-red-teaming lesson's "a hunt that finds nothing is still valuable" framing from Path 18: the value here is in the consistent practice and the visible track record, not in any single post being perfect.
:::

:::challenge Test yourself
Why does a technical post that honestly includes dead ends and failed attempts often read as more credible and useful than one showing only the final, working solution?
<details><summary>Show answer</summary>A reader facing a similar technical problem is very often somewhere in their own process of trying things that don't quite work — showing only a clean, final solution presents an idealized version of problem-solving that doesn't match most readers' actual lived experience of working through a hard technical problem, and it gives them no signal about whether their own current dead-end attempt is a normal, expected part of the process or a sign they're doing something fundamentally wrong. A post that honestly documents what was tried and why it didn't work, before arriving at what did, gives a reader something genuinely more useful: recognition ("oh, I hit that same wall") and a clearer sense of what actually distinguished the eventual working approach from the failed attempts, not just the final answer stripped of its reasoning. For someone evaluating this as a portfolio piece — a hiring manager or a fellow practitioner — the presence of genuine, specific dead ends also serves as a credibility signal in itself: it's far harder to fabricate a plausible, technically specific failed attempt than to describe a clean, hindsight-polished success, which is exactly why this kind of honesty tends to read as more trustworthy, not less impressive.</details>
:::

## Key terms

- **Process transparency** — honestly documenting dead ends and failed attempts, not just the final working solution.
- **Concept explainer** — writing to teach something you learned, which itself reveals and closes gaps in your own understanding.
- **Publishing consistency** — favoring regular, shipped, imperfect posts over rare, exhaustively polished but unpublished ones.

## Recap

- A well-written technical post demonstrates problem-solving process in a way a bare code repository or resume bullet can't.
- CTF write-ups, project deep-dives, concept explainers, and learning reflections are all genuinely strong, accessible post formats.
- The context/process/solution/takeaway structure mirrors Path 15's professional report-writing discipline, adapted for teaching.
- Consistent, honest, imperfect publishing beats rare attempts at a flawless post that never actually ships.
