Dependency / SBOM Risk Checker

Paste a dependency list and flag ones matching a known-vulnerable version range.

Most of the code in a modern application was written by strangers and pulled in automatically. A software bill of materials is the inventory of those strangers, and it is the difference between answering "are we affected?" in minutes or in weeks.

How to use it

  1. Paste dependencies one per line as name@version.
  2. Review the risk notes returned for each.

What to take away

Transitive dependencies are where the risk hides

You install twenty packages and get eight hundred. The vulnerable one is almost never a package you chose deliberately.

Pin versions, then update them deliberately

Unpinned ranges mean your build is not reproducible and a compromised release can arrive without any change on your side.

Reachability changes severity

A critical CVE in a code path your application never calls is real but not urgent. Deciding that honestly is what stops alert fatigue.

Frequently asked questions

What is an SBOM?

A machine-readable list of every component in your software, with versions and often licences. SPDX and CycloneDX are the two common formats, and both are increasingly required by procurement.

Why did Log4Shell matter so much?

Because a critical flaw sat in a library embedded so deeply and so widely that most organisations genuinely could not tell whether they used it. That inability to answer was the crisis, more than the bug.

Is this a real vulnerability scanner?

No — it is a teaching aid using a small illustrative dataset. Real work uses live advisory feeds through tools like Dependabot, Trivy, Grype or Snyk.
